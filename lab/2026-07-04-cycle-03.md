## What hypothesis was tested?

That the 14 CCI invariants (I1–I14), derived from the Finance domain, generalize to an independent domain: a GTK4 desktop application's dashboard rendering pipeline. ### Four unexpected discoveries

1. **Digest fast-skip**: A 7-field digest (`focus_mode`, `tile_mode`, `coach_pick_topic`, `exam_date`, `current_topic`, `has_chapters`, `onboarding`) can skip the entire dashboard render. No equivalent in CCI — the runtime always runs unconditionally.

2. **Materialized views**: Single-pass derived caches (`_parsed_progress`, `_sorted_competence`, `_srs_overdue_by_ch`, etc.) computed before any widget is built. CCI has no preprocessing phase — data flows trace → interpreter → output without pre-aggregation.

3. **On-demand lazy charts**: Three sections (activity chart, concept forest, cognitive trace) are hidden behind buttons — computed only on user click. CCI is always eager.

4. **Guard-centric refresh**: Three independent mechanisms to avoid rendering (entry gate, digest skip, rate limiter at 0.8s). CCI has no pre-execution guards. The GUI optimizes by *not doing work*; CCI optimizes by *producing immutable evidence*.

## What surprised us?

1. **3 refuted predictions**: P3 (provenance), P10 (step return shape), P11 (dual protocol) did not generalize. These may be CCI-specific patterns rather than universal architectural invariants. The GUI simply doesn't need provenance tracking — it uses a flat `update_dashboard()` with no `reason` parameter.

2. **The "avoid vs. produce" philosophical gap**: The GUI has three independent mechanisms to avoid rendering. CCI has zero pre-execution guards. This suggests a fundamental architectural choice point: *should a system try to avoid work, or should it execute unconditionally and let downstream consumers decide?* The CCI chose the latter; the GUI chose the former. These may be domain-specific optimizations, or there may be a meta-principle about when each strategy is appropriate.

3. **Materialized views as a missing architectural concept**: CCI assumes data flows through a pipeline (trace → interpreter → output). The GUI demonstrates a materialized view pattern (pre-aggregate once, consume many times) that doesn't exist in the CCI architecture. This may be a general optimization pattern that CCI should support.
